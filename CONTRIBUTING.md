## How to contribute
We'd love to accept your patches and contributions to this project. There are just a few small guidelines you need to follow.

## Preparing a pull request for review
Ensure your change is properly formatted by running:

```gradle
./gradlew spotlessApply
```

Then dump binary API of this library that is public in sense of Kotlin visibilities and ensures that the public binary API wasn't changed in a way that make this change binary incompatible.

```gradle
./gradlew apiDump
```

Crayfish also checks that every published type is named by at least one test, that the published artifacts contain no native code, and that the AAR's baseline profile holds only this library's classes:

```gradle
./gradlew apiCoverage
./gradlew :crayfish:verifyNoNativeCode
./gradlew :crayfish:verifyBaselineProfile
```

Please correct any failures before requesting a review.

## Running the tests
The shared tests run on several targets. The JVM one is the fastest to iterate on:

```gradle
./gradlew :crayfish:desktopTest
```

Coverage is measured on that same run:

```gradle
./gradlew :crayfish:desktopCoverageReport
```

The Android instrumentation tests need a connected device or a running emulator:

```gradle
./gradlew :crayfish:connectedAndroidDeviceTest
```

If you are changing decoding, geometry, or anything else that is shared, run the other targets too:

```gradle
./gradlew :crayfish:iosSimulatorArm64Test :crayfish:macosArm64Test :crayfish:wasmJsBrowserTest
```

## The stress suite

Breadth over the shapes that break croppers lives in `StressTest` on the desktop and `DeviceStressTest` plus `DeviceCropperStressUiTest` on a device: seven sources against eight crop rectangles each, degenerate rectangles, concurrent decodes, a close landing mid decode, sustained runs measured as steady state, and on the device a recreation storm and a tight crop and encode loop that reads every result back.

They need the generated fixtures, which the test tasks produce and push for you:

```gradle
./gradlew :crayfish:desktopTest --tests "com.github.skydoves.crayfish.e2e.StressTest"
ANDROID_SERIAL=<device> ./gradlew :crayfish:connectedAndroidDeviceTest
```

Two things to know before reading a red one. The Compose device tests cannot run on a locked phone: the lock screen bouncer holds window focus, every one of them fails with "No compose hierarchies found" or a timeout waiting for the crop node, and none of it is about the code. And the memory assertions are the ones to distrust first if they fail only in a full run, because `MemoryProbe` counts allocation process wide and a neighbouring test's threads land in the reading.

## Benchmarks and the baseline profile

The Android artifact ships a baseline profile, generated by driving the demo app through the journey in `benchmark/src/main/kotlin/.../CropperJourney.kt`. Regenerate it after changing that journey, or after a change large enough that the old rules no longer name the code that runs:

```gradle
./gradlew :crayfish:generateBaselineProfile
./gradlew :androidApp:generateBaselineProfile
```

Generation needs a rootable device, because the rule pulls the profile back with `adb root`. An `aosp` or `google_apis` emulator image, or any userdebug device, works; a Play Store image does not. The result is committed, so a regeneration shows up as a diff under `crayfish/src/androidMain/generated/baselineProfiles/`.

You do not have to run it by hand: the `Baseline profile` workflow does it on a Gradle managed device and opens a pull request with the diff. Run it from the Actions tab.

## What CI checks

`Android CI` runs on every pull request: `spotlessCheck`, `apiCheck` with `apiCoverage`, `assemble`, the two artifact gates, a build of the web demo, and the tests on desktop, macOS, iOS simulator and wasm. The Android instrumentation tests are not there, because they need a device and they are the ones that check native heap growth and recycled bitmaps.

`Publish Docs` deploys the mkdocs site and the wasm demo together on every push to `main`. They go out in one commit on purpose: `mkdocs gh-deploy --force` replaces `gh-pages` with a tree that is exactly `site/`, so anything pushed there separately would vanish on the next deploy.

`Publish` releases to Maven Central when a GitHub release is published.

The benchmarks are a separate run, and want a physical device rather than an emulator:

```gradle
ANDROID_SERIAL=<device> ./gradlew :benchmark:connectedBenchmarkReleaseAndroidTest
```

Each case runs twice, with the profile and without it. See [docs/performance.md](docs/performance.md) for what the current numbers are and what they do not cover.

## A note on tests
A test here is expected to be able to fail. If you add one, change the code it covers so that it goes red, then change it back. Several tests in this repository were found to be unable to fail for the thing they were written for, and each one was found that way rather than by review.

## Code reviews
All submissions, including submissions by project members, require review. We use GitHub pull requests for this purpose. Consult [GitHub Help](https://docs.github.com/en/github/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/about-pull-requests) for more information on using pull requests.
